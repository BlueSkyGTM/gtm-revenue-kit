# motions/dormant/ — the shelf contract

Five method skeletons that no account's motion currently runs. Mined from commercial GTM tool
suites during an evaluation that concluded *wire nothing, own the method*; these are the
surviving output. `README.md` is the catalog and holds the activation procedure; this file is
the contract.

| File | Activate when |
|---|---|
| `account-planning.md` | Contract sizes justify per-account planning across multiple stakeholders |
| `buyer-group-mapping.md` | More than one person must agree before a purchase |
| `champion-enablement.md` | A buyer must sell the purchase internally on your behalf |
| `demo-scripting.md` | The offer is demoable: software, a dashboard, a repeatable walkthrough |
| `mutual-action-plan.md` | Cycles run weeks to months against milestones both sides commit to |

## The one rule that governs this folder

**Do not load these in a working session.** They are inert by design. A framework loaded for a
motion you are not running produces advice shaped like the wrong sale: committee mapping on an
owner-led deal, a mutual action plan on a two-week cycle. The `Activate when:` line in each
file is the whole index, and reading it is not the same as loading the file.

## Entering and leaving

Activation is a core change, not an account change, and the steps are in `README.md`. The
short form: the file moves up into `motions/playbooks/`, and it localises by pointing at the
account's `context/` rather than by carrying a value (`foundations/principles.md` §3). Half
activated is worse than dormant, because the next reader cannot tell which state it is in.

Nothing is deleted from here. An account onboarded next month may activate on day one what
every current account ignores, which is what keeping the engine broader than any one tenant
is for.
