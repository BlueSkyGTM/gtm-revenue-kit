# Dormant playbooks — mined frameworks awaiting a motion that needs them

Each file here is a **method skeleton**, mined from commercial GTM tool suites during an
evaluation that concluded: wire nothing, own the method. The skeletons are the surviving output.
They are real frameworks that no account's motion currently runs.

Every file opens with an **`Activate when:`** line. That line is the whole index — read it and
you know whether the framework applies to the motion in front of you.

## Activating one

Dormant playbooks are core, so activation is a core change, not an account change:

1. An account's motion meets the trigger on the `Activate when:` line.
2. Move the file up into `motions/playbooks/` proper. It is now live for every account, which is fine —
   a playbook that does not apply to an account is simply never triggered there.
3. Localize by *pointing*, not by editing: the playbook names the file under
   `accounts/<slug>/context/` where each value is read from. It never carries the value itself.
   If a step cannot be written without a number, the number belongs in the account.

Do not localize a dormant playbook in place and leave it here. Half-activated is worse than
dormant, because the next reader cannot tell which state it is in.

## Until then

**Do not load these in a working session.** They are inert by design, and loading a framework
for a motion you are not running produces advice shaped like the wrong sale — committee mapping
on an owner-led deal, mutual action plans on a two-week cycle.

Dormant is not deleted. A new account onboarded next month may activate on day one what every
current account ignores. That is the point of keeping the engine broader than any one tenant.

Dormant playbooks are methods awaiting a motion — shelved, not deleted, so they are found instead of rebuilt.
