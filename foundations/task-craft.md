# Task craft — how an executable document is written here

*Provenance: read out of the upstream kit's skills (`baseline-gtm-starter-kit`), where
this craft is practiced but never stated. It is the most valuable thing the original
authors left, and it is tacit — this file exists so it survives restructuring. Admitted
under principle 1 as upstream-verified.*

Every skill, play, and pipeline stage in this kit follows six rules. When writing or
revising one, check against all six; when one reads badly, the missing rule is usually
which.

## 1. A cost/output contract in the header

`Duration: 20–40 min` · `Output: outputs/[date]-[account]-research.md` — before anything
else, the reader knows the price and the artifact. A task without a stated cost sprawls;
a task without a named output produces prose.

## 2. Quick Start above Purpose

The runnable one-liner comes *before* the explanation, and links a worked example of the
output where one exists. Copy-paste first, understand second — the document serves the
person mid-task, not the person browsing.

## 3. Purpose states the anti-goal

Name the failure mode the task steers around, not just the goal: *"The goal is not a
company summary you could get from their About page."* The anti-goal is what stops a
model from producing something task-shaped and empty.

## 4. Inputs carry reasons

Every input file justifies its own load: `context/icp-definition.md — to score fit`.
An inputs list without reasons invites bulk-loading; with reasons, a session can skip
what its variant of the task doesn't need.

## 5. Steps are time-boxed and sum to the header

`Step 1 (5 min) · Step 2 (10 min) · Step 3 (5 min)` against a 20–40 minute header. The
budget contract is why a task can't quietly grow a seventh step nobody priced.

## 6. Reasoning rides inline, in parentheses

*"(shorter tenure = more likely to be making changes)"* — the document teaches while it
directs, one clause at a time, in place. Reasoning banished to a separate rationale file
is reasoning nobody reads mid-task.

## The last gate

Form is not honesty. Before committing a task file — or anything else — to core, run
**`failure-modes.md` §The self-check**: six questions, ordered by how often each catches
something. The first (*does every claim trace to a stated source?*) is the one that
catches the most.

That gate catches what is broken. Whether the thing is *good* has its own home: judge it
against its pillar's criteria in `conceptual-framework.md` — every task serves a named
pillar, and the pillar says what a good output looks like.

## What this replaces

Structure lives in the ICM conventions (folders, contracts, the router) — not in the
task files. A task file spends its lines on the six things above; it never carries folder
maps, lineage notes, or governance. The two crafts compose: ICM says where a document
lives and what may load with it; this file says how the document itself is written.
