# Failure modes — how work goes wrong here, and the tell for each

*Provenance: distilled from the operation's calibration record — failures observed in
live sessions, each with the counter-rule it produced. Operator-proven (principle 1).
Swap-test clean: every entry is a general failure mode; the instances that produced them
stay in the operator's own record.*

**Run the self-check below before committing anything to core.** This file is a set of
checks, not a lens to narrate through — a draft that keeps announcing which failure mode
it is avoiding has produced the ceremony corruption in §3. Most of what follows was
learned by producing the failure, not by theorizing it.

---

## 1. The three shapes of a bad answer

**Too broad** → a modal, hedged answer. *Tell:* options offered before a conclusion is
stated.

**Too specific / forced** → confident punctuation on the same average. *Tell:* language
sharpens while the evidence stays flat.

**Too demanding** → **fabricated specificity**, and this is the dangerous one. Pressure
for an answer produces a missing fact, conveniently. *Tell:* a number, a name, a
citation, or a "standard term" appears exactly where the gap was, with no source. *Fix:*
refuse the pressure, name the gap, and give the cheapest test that would settle it.

Two live examples of the third, both caught: a framework presented as "the industry
standard term" for a practice that had no standard term — the phrase returned zero
results; and a demand for complete confidence about untested coverage, where the correct
answer was "no, and here is the test that would tell us."

## 2. The inference-as-fact class — the most persistent failure

**Fill a gap with a plausible inference, then act on it as established.** Six instances
on record, every one caught by the operator, **none by any check**. Each produced a
counter-rule:

| The inference | The counter-rule it produced |
|---|---|
| Motive inferred from an undone task | Challenge the work, never the person |
| A rule written against an unread file | Never legislate about something unread |
| A stage inferred from a verb in the request | Ask which stage; never infer from a verb |
| One unsupported item allowed to reframe a mostly-confirmed claim | Report the ratio |
| A term's cardinality inferred inside its own definition | A definition does not fence dimensions it does not mention |
| One party's approval gate promoted to a universal gate | **Every gate names its scope** |

**The class survives rules against its instances — expect a seventh.** The durable
defenses are structural, not moral: verification markers on every claim, declared slots
instead of implicit ones, and evidence attached to conclusions.

## 3. Corruption taxonomy

**Conviction corruption.** A stance stabilizes and the work starts manufacturing
certainty to protect it. *Tell:* the argument gets more confident as the evidence gets
older.

**Ceremony corruption.** A ritual fires regardless of stakes — rules written where
triggers belong. *Tell:* self-monitoring cannot catch it, because from inside, the
failure state feels identical to success.

**Compatibility corruption.** Agreement between voices optimized over truth-seeking;
disagreement treated as incompleteness. *Counter-rule:* disagreement is information —
resolve only if resolving changes what gets done. (This is why doctrinal conflicts become
tests rather than blends.)

**Caveat-weighted synthesis** — the inverse. One unsupported item found among several
confirmed ones, allowed to reframe the whole claim. Leading with the miss reads as rigor
and costs the same accuracy as leading with agreement. *Counter-rule:* report the ratio.
Two of three confirmed is "holds, with a note," not "overstated."

**Word-search as capability-search.** Checking a compressed source for a term and
reporting absence-of-word as absence-of-thing. *Counter-rule:* match on capability, not
vocabulary. The hardest version: auditing one layer of a system and reporting the result
as the whole system — a method built in markdown is not absent because no connector
exists for it.

**Citation outliving its source.** A citation and a verified reference look identical in
prose. A repository was cited as live across three documents after it had been deleted.
*Counter-rule:* claims about instruments carry a verification marker and a date, and are
cited from the one file that holds them — never restated.

**Centrality mistaken for height.** The most load-bearing artifact reads as the top of
the hierarchy; the strongest rule in one scope reads as the rule everywhere.
*Counter-rule:* importance and composition are different axes. Place a thing by what it
*is*, not by how much depends on it.

## 4. Contract versus disposition — the finite test

A **contract** is countable or checkable by something that can fail: `id, title, done`;
"every conclusion names a falsifier"; "the exception log has entries." A **disposition** —
"prefer reality contact," "respect the reader," "understand the domain" — cannot fail a
check. It can be selected for and measured after the fact, never enforced.

**Rules that cannot fail prove nothing.** Constrain interfaces and countable interior
properties; never contract the judgment itself.

The governance corollary: **a boundary produces signal when it binds, not when it
exists.** A suppression pass that kills a large fraction of a sourced list is information
about the sourcing. An exclusion rule that has never rejected anything is decoration.
Gates get debugged like scoring does — possible only if they are written as rules that
could bind.

## 5. Load discipline failures

The rules are `principles.md` §Load discipline. The failures they prevent:

**Rival rule systems co-loaded.** Copy rules loaded during a scoring pass make the work
argue for what sounds good; scoring values loaded during a copy pass produce output that
reads like a rubric. The same holds for any two rule sets that judge each other's
outputs.

**Bulk-loading a folder is how a session runs out of room and starts inventing.** The gap
between running out of context and fabricating is short — §1's third shape is often just
a session that filled up.

**Delivery rules from a host system loaded into a motion session.** A session that loads
a write gate starts asking permission to send an email; one that loads copy rules starts
editing records for tone.

## The self-check, in order

Before committing anything to core, in order of how often each catches something:

1. **Does every claim trace to a stated source?** If a mechanic appears that is in neither
   the source material nor a recorded ruling, it is fabricated — remove it or mark it as
   the drafter's rendering.
2. **Did anything get inferred and then used as established?** Especially scope, stage,
   status, or an undefined dimension of a defined term.
3. **Can each rule fail?** If not, it is a disposition wearing a contract's clothes.
4. **Is the ratio reported?** Not just the miss.
5. **Does it name what waste it prevents?** If not, it is reference, not law.
6. **Would it survive the swap test?** Read it as if a different account owned it.

The six catch what is wrong. Whether the thing is *good* is a different question with a
different home — its pillar's criteria in `conceptual-framework.md`. Run both.
